# jarvEducation — Συμβάσεις έργου

Οι κανόνες που δεν είναι αρχεία. Ο καθένας υπάρχει επειδή, αν αφεθεί στην
κρίση της στιγμής, παράγει απόκλιση.

**Δύο προελεύσεις, και η μία υπερισχύει.** Οι ενότητες **§2–§9** είναι
**προϋπάρχουσες συμβάσεις αυτού του project**, που ίσχυαν και δούλευαν πριν
γραφτεί αυτό το αρχείο (πηγή: `CLAUDE.md`, σχόλια στον κώδικα, ιστορικό
commits) — μεταφέρθηκαν εδώ αυτούσιες. Οι ενότητες **§10–§18** προέρχονται από
το cross-project engineering operating model. Το operating model είναι
**πρόταση για projects που δεν έχουν δικές τους συμβάσεις — όχι κανόνας που
επιβάλλεται πάνω σε ένα υπάρχον σύστημα που λειτουργεί**: όπου τα δύο
συγκρούονται, **υπερισχύει η υπάρχουσα σύμβαση** και η απόκλιση σημειώνεται
επιτόπου.

Το σκεπτικό δεν ζει εδώ. Ζει στο `docs/engineering-log.md`· οι αποφάσεις στο
`docs/adr/`.

## 1. Στρώματα τεκμηρίωσης

| Στρώμα | Πού | Διάρκεια ζωής |
|--------|-----|----------------|
| Ανοιχτά items | `todo.md` → `todo.archive.md` | Εφήμερα· τα ids μόνιμα |
| Αποφάσεις | `docs/adr/` | Αμετάβλητες μόλις γίνουν accepted |
| Πλήρες σκεπτικό | `docs/engineering-log.md` | Ζωντανό, επεξεργάζεται επιτόπου |
| Specs / plans | `docs/superpowers/{specs,plans}/` | Παγωμένα, με ημερομηνία στο όνομα |
| Context για AI-assisted development | `CLAUDE.md` | Ζωντανό |
| Έγγραφα κατάστασης | βλ. §13 | Ξαναγράφονται σε κάθε παράδοση |
| Έγγραφα διαφορών | βλ. §13 | Παγώνουν μόλις γραφτούν |

Η σχέση ADR ↔ log είναι μονόδρομη: το ADR δείχνει στο log για το πλήρες
σκεπτικό, το log δεν εξαρτάται από το ADR. Κανένα από τα δύο δεν υποκαθιστά το
άλλο.

Το `CLAUDE.md` παραμένει το σημείο εισόδου και **δεν αντικαθίσταται** από αυτά
τα αρχεία: κρατά το context του project και δείχνει εδώ για τις λεπτομέρειες.

## 2. Η τράπεζα ερωτήσεων δεν επεξεργάζεται ποτέ χειροκίνητα

**Προϋπάρχουσα σύμβαση.** Τα `src/data/questions-{a..f}.json` παράγονται από το
`scripts/generate-questions.mjs` (seeded RNG, deterministic). Αλλαγή
περιεχομένου σημαίνει:

1. Επεξεργασία του `scripts/generate-questions.mjs`.
2. `node scripts/generate-questions.mjs`.
3. **Commit του script και των JSON μαζί, στο ίδιο commit.**

Χειροκίνητη επεξεργασία JSON χάνεται στην επόμενη παραγωγή, σιωπηλά. Αν μια
διόρθωση φαίνεται «πολύ μικρή για να πειράξω τον generator», είναι ακριβώς η
περίπτωση που δημιουργεί απόκλιση μεταξύ script και δεδομένων.

Δύο συνέπειες που πρέπει να ελέγχονται πριν από μια αλλαγή που προσθέτει ή
αφαιρεί ερωτήσεις: τα ids είναι αύξοντες αριθμοί ανά κατηγορία, οπότε
**μετατοπίζονται**, και τα ids είναι τα κλειδιά των documents στο `feedback`
collection του Firestore. Βλ. ADR-0002.

## 3. Κανόνες ποιότητας ερωτήσεων

**Προϋπάρχουσα σύμβαση.** Έχουν ζητηθεί ρητά και ισχύουν για κάθε νέα ή
τροποποιημένη γεννήτρια ερωτήσεων. Δεν χαλάνε:

- **Ρήματα σε χρόνους:** κύρια απάντηση σε **α' ενικό** (παίζω → έπαιξα)·
  δεκτό και γ' ενικό στις ερωτήσεις κειμένου. Οι επιλογές πολλαπλής επιλογής
  είναι όλες σε α' ενικό.
- **Συμπλήρωση γραμμάτων:** τόσες παύλες όσα και τα γράμματα που λείπουν
  (`πληρών_` → «ω», `θάλα__α` → «σσ»)· απάντηση = μόνο τα γράμματα, αλλά
  γίνεται δεκτή και ολόκληρη η λέξη.
- **Ανοιχτές ερωτήσεις με πολλές σωστές απαντήσεις:** λίστα `acceptedAnswers`
  (αισθήσεις, νησιά, ποτάμια, ανακυκλώσιμα, συνώνυμα, παραλλαγές μονάδων…).
- **Αντικείμενα προβλημάτων (ITEMS):** μόνο **ουδέτερα πληθυντικού**, ώστε το
  «Πόσα …» να είναι πάντα σωστό.
- **Ονόματα με σωστό άρθρο** (Ο Νίκος / Η Μαρία) και **σωστές πτώσεις** στις
  εκφωνήσεις (π.χ. «στον Αόριστο»).
- **Ύλη αυστηρά ανά τάξη** (π.χ. όχι περίμετρος στην Α'· Ιστορία/Θρησκευτικά
  μόνο από τη Γ' και μετά, Γεωγραφία/Φυσικές Επιστήμες μόνο από την Ε').
- Τα μαθήματα προστίθενται **προσθετικά** ανά τάξη: Α'/Β' = 500, Γ'/Δ' = 600,
  Ε'/ΣΤ' = 700 ερωτήσεις.
- Οι επιλογές μαθημάτων στο UI παράγονται από την τράπεζα της τάξης, όχι από
  στατική λίστα — μια τάξη δεν εμφανίζει ποτέ μάθημα χωρίς ερωτήσεις.

Η βαθμολόγηση (`src/utils/grading.ts`) αγνοεί τόνους, κεφαλαία, τελικό σημείο
στίξης και αρχικό άρθρο, και **δεν πετάει ποτέ exception**. Αυτό είναι μέρος
του ίδιου στόχου με τα παραπάνω και δεν «σφίγγει» για λόγους καθαρότητας.

## 4. Πριν από κάθε push

**Προϋπάρχουσα σύμβαση.**

1. `npm run build` — τρέχει και `vue-tsc`. Πρέπει να περνάει.
2. **Οπτικός έλεγχος σε mobile viewport 375px** στο preview.

Το ίδιο `npm run build` τρέχει και στο CI, οπότε ένα σφάλμα τύπων δεν κάνει
κακό deploy — μπλοκάρει το deploy. Ο λόγος να τρέχει τοπικά είναι να μη
σπαταλιέται ένας κύκλος CI, και κυρίως ο οπτικός έλεγχος, τον οποίο **κανένα
βήμα του CI δεν κάνει**.

Αυτή είναι η πρόβα πριν από το live για αυτό το project (βλ. §14).

## 5. Commits και γλώσσα

**Προϋπάρχουσα σύμβαση.**

- Τα commit messages είναι **στα αγγλικά** και τελειώνουν με γραμμή
  `Co-Authored-By: <μοντέλο> <noreply@anthropic.com>`. Το όνομα είναι του
  μοντέλου που έκανε πράγματι τη δουλειά — στο ιστορικό υπάρχουν ήδη
  `Claude Fable 5`, `Claude Fable 5.1` και `Claude Sonnet 5`, οπότε η γραμμή
  δεν είναι σταθερό αλφαριθμητικό που αντιγράφεται αυτούσιο.
- Η **επικοινωνία με τον χρήστη γίνεται στα ελληνικά**.
- Η **τεκμηρίωση αυτού του repo είναι στα ελληνικά** (`CLAUDE.md`, `README.md`,
  `docs/`). Τεχνικά αναγνωριστικά, διαδρομές αρχείων και κώδικας μένουν
  αυτούσια — συμπεριλαμβανομένων των ονομάτων αρχείων στο `docs/adr/`.

*Απόκλιση από το πρότυπο: το πρότυπο repo (`geoQuiz`) έχει την τεκμηρίωσή του
στα αγγλικά. Εδώ υπερίσχυσε η υπάρχουσα γλώσσα του project.*

## 6. `vite.config.ts`: το `base: './'` δεν αλλάζει

**Προϋπάρχουσα σύμβαση.** Το `base` είναι **σχετικό** (`'./'`) από το αρχικό
commit. Ο λόγος δεν είναι καταγεγραμμένος πουθενά στο repo (βλ. engineering log
§2), αλλά η σύμβαση «δεν αλλάζει» είναι ρητή στο `CLAUDE.md` και τηρείται.

Αν κάποτε προκύψει πραγματικός λόγος να αλλάξει, γράφεται νέο ADR — δεν
αλλάζει επειδή «έτσι το θέλει το εργαλείο».

## 7. Ο φάκελος `.vs/` δεν είναι πηγαίος κώδικας

**Προϋπάρχουσα σύμβαση.** Ο χρήστης δουλεύει σε **Visual Studio**. Ο `.vs/`
είναι στο `.gitignore` και εξαιρείται και από τον file watcher του dev server
(`vite.config.ts`) — το VS κλειδώνει αρχεία εκεί και ρίχνει το `npm run dev` με
`EBUSY`.

Ό,τι εμφανίζεται μέσα στο `.vs/` δεν είναι αλλαγή, δεν γίνεται commit και δεν
«καθαρίζεται».

## 8. Το Firebase SDK μένει εκτός του main bundle

**Προϋπάρχουσα σύμβαση.** Το SDK φορτώνεται **δυναμικά**, μέσω της
`getFirebase()` στο `src/firebase/index.ts` και μέσω `await import(...)` μέσα
στις συναρτήσεις του `src/services/cloud.ts` και του `useAuth.ts`.

Ένα στατικό `import` από `firebase/*` σε κώδικα της αρχικής φόρτωσης ακυρώνει
τη ρύθμιση **χωρίς να σπάσει τίποτα ορατό** — το μόνο σύμπτωμα είναι ένα
μεγαλύτερο bundle. Επίσης, κάθε cloud μονοπάτι πρέπει να αντέχει config `null`
(η εφαρμογή οφείλει να δουλεύει πλήρως χωρίς cloud).

Ομοίως lazy: οι τράπεζες ερωτήσεων ανά τάξη (`useGradeBanks.ts`) — μια τάξη
κατεβαίνει μόνο όταν επιλεγεί.

## 9. Αποφάσεις προϊόντος που δεν επαναδιαπραγματεύονται σιωπηλά

**Προϋπάρχουσες αποφάσεις χρήστη.** Ισχύουν μέχρι να γραφτεί νέο ADR:

- **Firestore**, όχι Supabase (το δωρεάν παγώνει σε αδράνεια), όχι Data
  Connect/SQL (κοστίζει μετά το trial). ADR-0003.
- **Βαθμολογία:** φωτογραφία προφίλ **ναι** (νομική βάση: γονική συναίνεση),
  όνομα **μόνο** «Μικρό Α.». ADR-0004.
- **Η σελίδα απορρήτου δεν ονομάζει Firebase ή Google** — μόνο «διακομιστές
  εντός της ΕΕ». ADR-0004.
- **Email επικοινωνίας:** `quizgame@jarvantage.com` (στο `PrivacyScreen.vue`).
- **Anti-cheat / server-side scoring:** **μόνο** αν εμφανιστούν ύποπτα σκορ.
  Δεν είναι προγραμματισμένη δουλειά.

## 10. Τα σχόλια κώδικα δηλώνουν την απόφαση, όχι την προέλευσή της

Ένα σχόλιο λέει τι ισχύει και γιατί πρέπει να συνεχίσει να ισχύει. Δεν λέει
ποιος το ζήτησε, πότε, ή σε ποια συζήτηση. Αυτή η ιστορία ανήκει στο
`docs/engineering-log.md`.

```ts
// options must be strings — a couple of math generators pass raw numbers,
// which crashes grading.ts's normalizeAnswer()          <-- ναι

// ο χρήστης το ζήτησε στις 2026-09-03 επειδή πάγωνε το quiz   <-- όχι
```

Το repo το τηρεί ήδη σε αρκετά σημεία (`vite.config.ts`, `cloud.ts`,
`grading.ts`) — τα σχόλια αυτά είναι το πρότυπο, όχι εξαίρεση.

## 11. Η τεκμηρίωση ενημερώνεται με αναζήτηση, όχι από μνήμη

Όταν προσγειώνεται μια αλλαγή, ψάξε στο repo **αυτό που πράγματι άγγιξε** — τη
διαδρομή, τη ρύθμιση, τη σταθερά, το όνομα αρχείου — και ενημέρωσε κάθε
έγγραφο που εμφανίζεται. Όχι τα έγγραφα που *θυμάσαι* ως σχετικά· έτσι
παλιώνει το τρίτο.

Σε αυτό το repo υπάρχουν τουλάχιστον τέσσερα σημεία που περιγράφουν τα ίδια
πράγματα και ξεχνιούνται εύκολα: `CLAUDE.md`, `README.md`, τα σχόλια στην
κορυφή του `generate-questions.mjs`, και το κείμενο του `PrivacyScreen.vue`.

## 12. Εκδόσεις

Το `package.json` έχει `version` και **αυτή η έκδοση είναι ορατή στον χρήστη**:
το `vite.config.ts` την περνάει ως `__APP_VERSION__` και η σελίδα Απορρήτου
δείχνει `v <version>.<yymmddHHmm>` (το δεύτερο μέρος είναι build timestamp σε
UTC, αυτόματο). Δεν υπάρχει κανένα git tag σήμερα.

**Το trigger αύξησης είναι ένα tagged release.** Κάθε git tag στο `main` είναι
release και ανεβάζει τουλάχιστον το patch. Ανεβάζει **minor** ένα release που
αλλάζει το σχήμα των δεδομένων ερωτήσεων — το `Question` interface, ή τα ids
των ερωτήσεων, από τα οποία εξαρτώνται το αποθηκευμένο ιστορικό και τα
documents του `feedback`. Τίποτα άλλο δεν ανεβάζει τίποτα, και το «αυτό μου
φαίνεται μεγάλο feature» δεν είναι trigger.

**Tag πριν το publish, όχι μετά.** Το tag μπαίνει στο ακριβές commit που
δημοσιεύεται, πριν από το deploy. Το `git push` **δεν** στέλνει tags από μόνο
του — θέλει ρητό push.

Το tag και το `package.json version` είναι **δύο πηγές που πρέπει να
συμφωνούν**, και η δεύτερη τυπώνεται σε παραδοτέα σελίδα. Μη βασίζεσαι στο να
θυμηθείς να ενημερώσεις και τα δύο· όταν μπει test layer (§15), η σύγκριση των
δύο είναι φθηνός και προφανής έλεγχος.

*Απόκλιση από το πρότυπο: το πρότυπο υποθέτει project «χωρίς version constant
πουθενά». Εδώ υπάρχει και εμφανίζεται σε χρήστη, οπότε ο κανόνας γράφτηκε γύρω
από το υπάρχον.*

## 13. Έγγραφα κατάστασης vs έγγραφα διαφορών

Αποφασίζεται τώρα, ώστε να μη χρειαστεί να το εφεύρει η πρώτη παράδοση.

**Έγγραφα κατάστασης** περιγράφουν την *τρέχουσα* κατάσταση και ξαναγράφονται
ολόκληρα σε κάθε παράδοση: οδηγός deployment, αρχιτεκτονική, εγχειρίδιο
χρήστη/γονέα αν χρειαστεί ποτέ. Το καθένα φέρει σφραγίδα έκδοσης. Ένα έγγραφο
κατάστασης **δεν** περιέχει ποτέ τη φράση «σε αυτή την έκδοση» ή «νέο» — αυτό
το κείμενο γίνεται σιωπηλά ψευδές χωρίς να φαίνεται λάθος.

**Έγγραφα διαφορών** είναι τα release notes: ένα αρχείο ανά έκδοση κάτω από
`docs/releases/`, με το όνομα της έκδοσης, παγωμένο μόλις γραφτεί. Περιγράφει
μόνο ό,τι κυκλοφόρησε και ο αναγνώστης ήδη ξέρει ή ζήτησε. Εσωτερικά ευρήματα
που δεν ανέφερε κανείς έξω δεν μπαίνουν.

Κανένα από τα δύο δεν υπάρχει ακόμα και κανένα δεν πρέπει να δημιουργηθεί πριν
υπάρξει παράδοση να περιγραφεί. Στην πρώτη παράδοση, πρώτα το έγγραφο
διαφορών.

## 14. Κλάδοι και tags

Το **`main` είναι ό,τι είναι ζωντανό**. Το GitHub Actions workflow το χτίζει
και το δημοσιεύει σε κάθε push (ADR-0001), σε περίπου ένα λεπτό, χωρίς καμία
πύλη ενδιάμεσα. Δεν υπάρχει staging branch.

Το διακύβευμα εδώ είναι πραγματικό και όχι θεωρητικό: η εφαρμογή χρησιμοποιείται
από **παιδιά**, έχει **ζωντανό Firestore** και **δημόσια Βαθμολογία**. Ένα
commit στο `main` φτάνει σε αυτά.

Άρα το `main` δεν είναι μέρος για να παρκάρει δουλειά σε εξέλιξη. Η πρόβα πριν
από το live είναι αυτή της §4 (`npm run build` + οπτικός έλεγχος 375px) — το
GitHub Pages δεν προσφέρει preview deployment ανά branch, οπότε δεν υπάρχει
τίποτα άλλο να τρέξει.

*Απόκλιση από το πρότυπο: το πρότυπο ορίζει ως πρόβα το preview deployment του
branch. Δεν υπάρχει τέτοιο εδώ· υπερίσχυσε η υπάρχουσα, δοκιμασμένη σύμβαση
της §4.*

Δύο συμπεριφορές του workflow που πρέπει να είναι γνωστές πριν από ένα push:
το `concurrency: cancel-in-progress` σημαίνει ότι δύο γρήγορα διαδοχικά push
ακυρώνουν το πρώτο deploy, και ο `vue-tsc` τρέχει μέσα στο build — άρα ένα
σφάλμα τύπων δεν βγαίνει ζωντανό, αποτυγχάνει.

Κάθε branch ή tag του οποίου το όνομα παύει να σημαίνει το προφανές, παίρνει το
νέο του νόημα γραμμένο εδώ, μία φορά, ρητά.

## 15. Στρώματα ελέγχου (tests)

Δεν υπάρχει κανένα σήμερα, και κανένας linter. Ο μόνος αυτόματος έλεγχος είναι
ο `vue-tsc` μέσα στο `npm run build`.

**Κάθε στρώμα πρέπει να δικαιολογείται από ένα συγκεκριμένο δομικό κενό που το
από κάτω στρώμα δεν καλύπτει, γραπτώς, πριν προστεθεί.** Το «έτσι μοιάζει μια
πυραμίδα ελέγχων» δεν είναι δικαιολογία.

Το πρώτο στρώμα έχει ήδη ονομαστεί, και το κενό του έχει ήδη προκαλέσει
πραγματικό bug σε παραγωγή (engineering log §7): τα παραγόμενα JSON **δεν
ελέγχονται ποτέ** ως προς το `Question` interface — το `useGradeBanks.ts` κάνει
`as Question[]` cast, οπότε ο TypeScript δεν βλέπει τίποτα, και ο generator
είναι απλό `.mjs` εκτός του `vue-tsc`. Ο έλεγχος τρέχει πάνω στα **πραγματικά
παραγόμενα αρχεία**, όχι σε επανυλοποίηση των κανόνων του generator — μια
επανυλοποίηση αποκλίνει από αυτό που τρέχει χωρίς να κοκκινίσει τίποτα.

Έλεγχοι που χρειάζονται setup το οποίο μπορεί να μην υπάρχει (μυστικό,
υπηρεσία σε λειτουργία) κάνουν **skip**· δεν κοκκινίζουν. Ένας κόκκινος
έλεγχος πρέπει να σημαίνει ότι ο κώδικας είναι λάθος.

## 16. Ποιοτικά guardrails

Κάθε guardrail που μπαίνει ξεκινά από **μηδενική βάση**: κενή λίστα εξαιρέσεων
και ταβάνι μηδέν. Καμία «κληρονομημένη» λίστα επιτρεπόμενων παραβάσεων — τέτοια
λίστα μόνο μεγαλώνει.

Το ταβάνι ζει στο **ίδιο αρχείο** με τον έλεγχο που το επιβάλλει, ώστε το
χαλάρωμά του να φαίνεται στο diff εκείνου του αρχείου και να μην περνάει ως
αλλαγή ρύθμισης.

## 17. Εσωτερικό vs παραδοτέο περιεχόμενο

Ό,τι είναι στο `docs/` είναι **εσωτερικό** και δεν φτάνει ποτέ σε χρήστη.

Οι παραδοτέες επιφάνειες αυτού του project είναι η ίδια η εφαρμογή και, ειδικά,
**η σελίδα Απορρήτου** — η οποία έχει ρητό, δεσμευτικό κανόνα περιεχομένου:
**δεν ονομάζει Firebase ή Google servers**, μόνο «διακομιστές εντός της
Ευρωπαϊκής Ένωσης» (ADR-0004). Η σελίδα δείχνει επίσης τη σφραγίδα έκδοσης
(§12), οπότε ένα λάθος εκεί είναι ορατό σε γονείς.

Πριν φύγει οτιδήποτε προς τα έξω, διαβάζεται. Αν κάποτε υπάρξει πραγματική
εξαγωγή κειμένου (release notes, εγχειρίδιο), μπαίνει και μηχανικό δίχτυ:
έλεγχος για εσωτερικούς-μόνο όρους μέσα στο εξαγόμενο κείμενο. Δίχτυ, όχι
υποκατάστατο της ανάγνωσης.

## 18. Ρυθμίσεις αντί για μαντεψιές — και ρυθμίσεις εκτός git

Μια τιμή που είναι αβέβαιη ή πιθανό να αλλάξει γίνεται **ρύθμιση**, χωρίς να
χτιστεί υποδομή configuration που δεν ζήτησε κανείς. Μία σταθερά σε ένα
προφανές σημείο μετράει ως ρύθμιση — π.χ. `MAX_SIGNUP_SLOTS` στο
`src/services/cloud.ts`.

Ξεχωριστό και σοβαρότερο: **υπάρχουν ρυθμίσεις που η εφαρμογή χρειάζεται για να
λειτουργήσει και ζουν εκτός version control** — Firestore security rules
(Firebase Console), custom domain του GitHub Pages (ρυθμίσεις repo· δεν υπάρχει
αρχείο `CNAME` στο repo), authorized domains του Firebase Auth. Μια αλλαγή εκεί
δεν αφήνει ίχνος σε κανένα diff και δεν αναιρείται με `git revert`.

Ο κανόνας δεν είναι «μετακίνησέ τα μέσα στο git» — είναι ότι **κάθε τέτοια
ρύθμιση που εισάγεται ή αλλάζει, γράφεται στην τεκμηρίωση του repo**, ώστε να
μπορεί να ξαναστηθεί. Το ADR-0001 επιβάλλει την υποχρέωση· η engineering log
§10 κρατά τη σημερινή λίστα.

*Προσθήκη πέρα από το πρότυπο, ειδική για αυτό το repo: το πρότυπο δεν έχει
αντίστοιχη ενότητα, γιατί εκεί δεν υπάρχει backend ούτε κονσόλα να ξεχαστεί.*

## 19. Καταστροφικές ενέργειες

Ό,τι είναι καταστροφικό απαιτεί **ρητή τιμή τη στιγμή της χρήσης**. Καμία
σημαία που ενεργοποιεί καταστροφή δεν μένει αναμμένη μέσα σε committed αρχείο
ρυθμίσεων, όπου είναι αόρατη τη στιγμή που ενεργεί.

Το repo έχει ήδη ένα πραγματικό παράδειγμα που ορίζει το πρότυπο: η διαγραφή
λογαριασμού (`useAuth.deleteAccount`) ζητά επιβεβαίωση σε modal, και σβήνει
**cloud δεδομένα πρώτα, τον Auth λογαριασμό τελευταίο**, ώστε μια αποτυχία να
μην αφήνει ποτέ χρήστη αποσυνδεδεμένο με ορφανά δεδομένα. Η σειρά αυτή δεν
αντιστρέφεται για λόγους «καθαρότερου» κώδικα.
